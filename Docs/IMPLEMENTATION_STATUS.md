# 구현 현황

검토일: 2026-09-07. C++ 소스·설정의 정적 검토, 에디터 타깃 빌드, 명령행 맵 로드와 사용자 실행 확인을 함께 기록합니다.

이 문서는 현재 구현 사실과 연결 누락을 기록합니다. 제품 기획, 기능 우선순위, 1차 목표를 정하지 않습니다. 구조와 위치는 [프로젝트 구조](PROJECT_MAP.md), 준수할 개발 규칙은 [개발 규칙](CONVENTIONS.md)을 참고합니다.

## 판정 기준

- **코드 경로 확인:** 함수 구현과 C++ 호출 관계를 확인함. 실행 성공을 뜻하지 않음.
- **실행 확인:** 실제 제작 UI에서 해당 흐름을 조작해 결과를 확인함. 확인한 범위 밖의 전투·패키징 성공을 뜻하지 않음.
- **부분 구현:** 데이터·함수·UI 중 일부는 있지만 호출 연결이나 실제 처리가 부족함.
- **규칙 미준수:** 개발 규칙과 다른 구현을 확인함. 규칙 자체의 오류와 구분함.
- **실행 검증 필요:** 블루프린트, 에셋 또는 실제 실행을 확인해야 최종 판단할 수 있음.

C++ 호출이 없다는 기록은 블루프린트 호출까지 없다는 단정이 아닙니다. 아래 영향 설명 중 조건부 표현은 재현 완료된 버그가 아닌 코드상 위험을 뜻합니다.

## 데이터와 저장

근거: [리소스 조회](../Source/SkillMaker/Game/SKDataManagerSubsystem.cpp), [저장 서브시스템](../Source/SkillMaker/Game/SKSaveGameSubsystem.cpp), [SaveGame 객체](../Source/SkillMaker/Save/SKPlayerSkillSave.cpp).

- `FSKWeaponData`, `FSKAnimationData`, `FSKProjectileData`는 현재 조회에 사용하는 데이터 테이블 행 구조체입니다. 레거시로 분류하는 것은 `USKDataManager`와 `USKSkillManager`입니다.
- 무기는 `FGameplayTag`, 애니메이션 호환 범위는 `FGameplayTagContainer`를 사용합니다. 몽타주·썸네일·발사체 클래스는 목록과 저장 과정에서 소프트 참조를 유지합니다.
- 기존 데이터 테이블의 문자열 무기 타입과 하드 발사체 클래스 값, 기존 SaveGame의 `WeaponType`은 새 필드로 자동 이관되지 않습니다. 사용자가 확인한 제작 흐름에 필요한 현재 값은 동작하지만, 아직 사용하지 않은 행과 이전 테스트 슬롯은 별도로 점검해야 합니다.
- 스킬 목록과 단일 스킬 조회·저장은 `CurrentSkillSet.Skills`를 사용합니다. 키는 `SkillID`이며 표시 이름은 `SkillName`입니다.
- 신규 저장 시 ID가 없으면 HUD가 저장 후보에 GUID를 생성합니다. 기존 ID가 있으면 같은 키에 저장합니다. 사용자가 ID를 직접 입력하는 C++ UI 경로는 없습니다.
- 기본 슬롯은 [서브시스템 헤더](../Source/SkillMaker/Game/SKSaveGameSubsystem.h)의 `Test1`, UserIndex는 `0`입니다. `LoadData` 호출로 변경됩니다.
- 저장 파일이 없으면 객체를 생성하고 슬롯에 기록합니다. 파일 로드·캐스팅에 실패한 경우 `LoadData`는 경고 후 반환하며, 저장 요청의 `GetOrCreatePlayerSkillSave`에는 객체 생성 보완 경로가 있습니다.
- `PlayerSkills`는 이름을 키로 하는 스킬셋 맵입니다. `SetSkillSet`은 현재 스킬 맵을 해당 이름으로 복사합니다. Q/E/R/F 슬롯 배치를 저장하는 구조와는 별개입니다.
- `SaveAllSkillSet`은 현재 SaveGame 객체를 슬롯에 기록합니다. 이 함수가 슬롯 배치를 수집하거나 새로운 이름의 스킬셋을 생성하지는 않습니다.
- 스킬셋 생성·장착을 잇는 UI C++ 경로와 스킬 삭제 API는 확인되지 않았습니다. `DT_SkillData`에서 현재 저장소로 초기 데이터를 자동으로 주입·이관하는 활성 UI 경로도 확인되지 않았습니다.

## 제작 편집기 실행 확인

2026-09-06~07 사용자 실행 확인에서 다음 두 흐름이 정상 동작했습니다.

1. 스킬 생성 → 무기 선택 → 애니메이션 선택 → 이펙트 선택 → 애니메이션 트리거 선택 → 스킬 미리보기 → 스킬 저장
2. 스킬 수정 → 저장 스킬 선택 → 기존 무기·애니메이션 선택 확인 또는 변경 → 세부사항의 기존 값 확인 또는 변경 → 스킬 미리보기 → 스킬 저장

이 확인으로 신규 스킬과 기존 스킬 모두 HUD의 단일 `CurrentEditingSkill`을 통해 선택값을 유지하고 저장하는 기본 제작 흐름은 사용할 수 있는 상태로 판정합니다. 수정 흐름에서는 저장 데이터를 불러온 뒤 무기 → 애니메이션 → 세부사항 순서로 이동하며, 기존 선택 상태를 확인하고 필요한 항목만 바꿀 수 있습니다. 현재 완료된 항목과 남은 기능 개발 범위는 아래에 기록합니다.

### DONE-UI-01: 세부사항 UI 개편

- 기본 탭은 유지하고 이번 프로토타입의 `TargetingType` 기본값을 `NonTarget`으로 고정했습니다. 기존 최소·최대 사거리 필드와 코드는 보존하되 WBP의 슬라이더와 문구는 C++에서 숨깁니다.
- 기본 탭의 아래쪽 항목이 잘리지 않도록 WBP를 `GeneralTabPanel > GeneralTabScrollBox > GeneralTabContent`로 구성하고 스크롤바와 마우스 휠 이동을 제공합니다. C++은 위젯을 재배치하지 않고 콘텐츠 상단·우측·하단 여백만 적용합니다.
- 탭 전환은 `WidgetSwitcher`의 자식 순서 대신 각 패널 참조를 사용하고, 현재 탭 버튼을 다른 선택 카드와 같은 파란색으로 표시합니다.
- 기존 디버프 탭의 WBP 컨테이너는 에셋 호환을 위해 이름을 유지하면서 화면 문구와 목록을 속성 선택으로 교체했습니다. 상태이상 데이터와 독립 카드 클래스는 삭제하지 않았습니다.
- 화염·물·바람·대지 Gameplay Tag를 추가하고 네이티브 속성 카드에서 한 가지만 선택하도록 구현했습니다. 선택 상태는 HUD의 `CurrentEditingSkill.ElementTag`에 즉시 반영되고 수정 화면에서 복원됩니다.
- 속성 카드는 전체 행을 하나의 버튼으로 사용합니다. 이름은 검은색 왼쪽 정렬로 표시하고, 선택 시 체크 표시와 속성색 배경을 함께 갱신하며, 설명은 글자 크기 15의 마우스 오버 툴팁으로 제공합니다.
- 발사체 행의 `SupportedElementTags`로 목록을 필터링합니다. 빈 컨테이너는 기존 데이터 호환을 위해 전체 속성을 지원하고, 속성 변경으로 기존 발사체가 호환되지 않으면 선택을 해제합니다.
- 카드 클릭 즉시 선택이 확정되므로 WBP에 남은 `ConfirmButton`은 선택 바인딩 없이 C++에서 숨깁니다.
- `WBP_SKSkillDetail`의 스크롤 계층과 네 탭 패널 바인딩을 로그로 확인했고, `SkillMakerEditor Mac Development` 빌드와 `SkillMakingMap` 명령행 로드가 성공했습니다. 사용자가 실제 WBP에서 탭 전환·선택 표시·속성 목록·단일 선택·툴팁·필터·숨김 처리가 의도한 수준으로 동작함을 확인했습니다.

### DONE-FX-01: 선택한 이펙트와 사운드의 미리보기 출력

- 트리거 노티파이는 선택한 `ProjectileActor`를 로드하고 발사체를 생성합니다. 생성 실패 시 클래스 이름과 함께 오류 로그를 남깁니다.
- 발사체 시작 시 Particle·Niagara 컴포넌트를 표시·활성화하고 `ProjectileSound`를 생성 위치에서 한 번 재생합니다. 시전자와 소유자는 충돌 대상에서 제외합니다.
- 사용자 실행 확인에서 선택한 트리거 시점에 발사체 이펙트와 사운드가 출력되고, 발사체가 타겟의 충돌 컴포넌트와 겹친 뒤 소멸하는 흐름을 확인했습니다.
- 속성 호환 필터는 구현했습니다. 속성별 실제 Niagara·머티리얼 색상 변경과 변경 허용 여부는 아직 미구현입니다.

### DONE-TRAIN-01: 제작·훈련장 맵 이동과 저장 스킬 목록 공유

- 제작 HUD와 훈련장 HUD에 네이티브 맵 이동 버튼을 추가해 각각 `SkillTrainingMap`과 `SkillMakingMap`을 엽니다.
- 훈련장 HUD는 제작 화면에서 이미 사용하던 `WBP_SKSkillSelection` 클래스를 재사용하고 실제 `ASKPlayerCharacter`를 선택 대상 플레이어로 전달합니다.
- 사용자가 `SkillTrainingMap`에서 `SkillMakingMap`으로 이동해 새 스킬을 제작·저장한 뒤 훈련장으로 돌아오는 왕복 흐름을 실행했습니다. 이 과정에서 방금 저장한 스킬이 훈련장 선택 목록에 온전한 상태로 표시되는 것을 확인했습니다.
- 훈련장에는 선택한 스킬을 Q/E/R/F 중 한 위치에 배치하는 네이티브 위젯과 플레이어·컨트롤러 등록 경로도 연결했습니다. 슬롯 배치 후 실제 키 입력 발동은 이 티켓의 실행 확인 범위에 포함하지 않습니다.
- 변경을 포함한 `SkillMakerEditor Mac Development` 빌드가 성공했습니다. 맵과 위젯 에셋의 편집·배치는 사용자가 Unreal Editor에서 담당합니다.

### DONE-TRAIN-02: 스킬 슬롯 배치·실행과 매핑 현황

- 저장 스킬을 선택하면 중앙의 네이티브 슬롯 위젯으로 전환하고 Q/E/R/F 중 원하는 위치에 배치합니다. 배치 후 UI를 닫고 GameOnly 입력으로 복귀합니다.
- 컨트롤러는 Q→슬롯 0, E→슬롯 1, R→슬롯 2, F→슬롯 3 연결을 C++ 런타임 Enhanced Input 액션으로 처리하고, `Started` 이벤트에서 한 번 실행합니다.
- 사용자가 슬롯 배치, 지정 키 입력, 스킬 몽타주·트리거·발사체 생성과 `BP_SKAI` 충돌까지 로그로 확인했습니다.
- `IA_OpenSkillChangeUI`는 `IMC_Default`에 설정된 숫자 0 매핑을 사용합니다. 숫자 0을 누르면 마우스가 활성화되고 현재 Q/E/R/F의 스킬 이름 또는 `비어 있음`을 표시합니다.
- 사용자가 현황 화면에서 `스킬 선택`을 눌러 저장 목록으로 이동하고, 다른 스킬을 슬롯에 재배치한 뒤 숫자 0으로 다시 열었을 때 변경된 매핑이 반영되는 것을 확인했습니다.
- 위젯·입력·데이터 조회·화면 전환은 단계별 `LogSkillMaker` 로그를 제공하며 `SkillMakerEditor Mac Development` 빌드가 성공했습니다.

### NEXT-ANIM-01: 일부 애니메이션 트리거가 목록에 표시되지 않음

- 트리거 목록은 `USKSkillAnimNotify_Trigger` 타입이면서 `NotifyTriggerName`이 `None`이 아닌 노티파이만 표시합니다. 일반 AnimNotify, 다른 노티파이 클래스, 이름이 비어 있는 항목은 의도적으로 제외됩니다.
- 누락된 몽타주마다 노티파이 클래스, `NotifyTriggerName`, 몽타주 이벤트 저장 상태를 확인해야 합니다.
- 현재 저장값은 시간이나 이벤트 ID가 아닌 `NotifyName` 하나이므로 같은 이름의 트리거가 한 몽타주에 여러 개 있으면 개별 지점을 구분할 수 없습니다.
- 완료 기준은 제작에 제공할 모든 트리거가 목록에 표시되고, 선택 상태가 복원되며, 선택한 한 지점만 미리보기에서 발동하는 것입니다.

### NEXT-PREVIEW-01: 미리보기 단계별 검증과 안내

- 현재 저장은 이름·무기·몽타주·발사체·트리거를 모두 검사하지만 미리보기는 프리뷰 캐릭터와 몽타주만 검사합니다.
- 애니메이션만 먼저 확인하는 부분 미리보기를 허용할지, 모든 필수 선택을 마친 완성 스킬 미리보기만 허용할지 UI 정책을 결정해야 합니다.
- 부분 미리보기를 유지한다면 이펙트나 트리거가 없을 때 애니메이션만 재생 중임을 사용자에게 알려야 합니다. 완성 미리보기라면 저장과 같은 필수값을 검사하고 누락 항목을 표시해야 합니다.
- 완료 기준은 현재 선택 상태에 맞는 미리보기 종류와 누락 항목을 사용자가 알 수 있고, 의도하지 않은 완성 결과로 오해하지 않는 것입니다.

### NEXT-DATA-01: Gameplay Tag 데이터 자동 검증

- 현재 실행 코드는 빈 무기 태그를 선택 경로에서 제외하고 빈 애니메이션 호환 태그를 일치하지 않는 값으로 처리하지만, 데이터 테이블 전체를 사전에 검사하지는 않습니다.
- 무기 행의 `WeaponTag`, 애니메이션 행의 `CompatibleWeaponTags`, `Weapon` 계층 포함 여부와 필수 몽타주 참조를 에디터 데이터 검증 또는 별도 검증 도구로 확인해야 합니다.
- 완료 기준은 잘못된 행의 데이터 테이블 이름, 행 이름과 문제 필드를 에디터에서 바로 확인할 수 있는 것입니다.

## 제작 UI의 연결 문제

### UI-01: 상세 편집값의 즉시 전달

근거: [제작 HUD](../Source/SkillMaker/UI/UI-SkillMaker/UEEditor/SKSkillMakerEditorHUD.cpp)의 `SetCurrentSkillData`; [상세 위젯](../Source/SkillMaker/UI/UI-SkillMaker/Common/SkillSelect/SKSkillDetailWidget.cpp)의 선택 콜백.

- 상세 위젯은 별도 스킬 데이터 멤버를 소유하지 않습니다. 유형·속성·발사체·노티파이 선택마다 HUD 최신값을 읽어 해당 필드만 변경하고 `OnSkillDetailChanged`로 전달합니다.
- HUD는 초기화·로드·전체 교체·개별 선택 변경 시 `OnEditingSkillChanged`를 발행하므로 현재 선택 요약 UI가 구독할 수 있습니다.
- `DamageTextBox`는 입력 변경 즉시 HUD의 최신 `FSKSkillData.DamageValue`를 갱신하고 기존 스킬의 저장값을 복원합니다. 범위 입력은 계속 레거시 주석 상태입니다.
- 입력값, HUD 반영값, 저장 후보, SaveGame 저장·조회와 훈련장 로드 시점에 `DamageValue`를 기록해 값이 유실되는 단계를 확인할 수 있습니다.
- 사용자가 기존 스킬에 `1000`을 입력한 뒤 같은 ID로 다시 저장하고 훈련장에서 조회했을 때 `DamageValue=1000.00`이 유지되는 것을 확인했습니다.
- C++ 빌드와 신규 생성·기존 수정의 선택·복원·저장 흐름, 개편된 세부사항 UI의 실제 동작을 확인했습니다.
- 델리게이트는 전체 `FSKSkillData`를 전달하지만 이벤트 순간 HUD 최신값으로 만든 지역 사본이므로 위젯에 오래된 편집 복사본이 남지 않습니다.

### UI-02: 신규 편집 초기화와 저장 ID 동기화

근거: [제작 HUD](../Source/SkillMaker/UI/UI-SkillMaker/UEEditor/SKSkillMakerEditorHUD.cpp)의 `BeginPlay`, `InitializeNewSkill`; [메인 위젯](../Source/SkillMaker/UI/UI-SkillMaker/UEEditor/SKSkillMakerEditorMainWidget.cpp)의 `OnCreateSkillClicked`, `OnSaveSkillClicked`.

- 새로 만들기 버튼은 무기 선택 화면으로 이동하기 전에 HUD 데이터를 초기화합니다.
- 기존 스킬을 선택하면 HUD에 저장 데이터를 불러온 뒤 무기 선택 화면으로 이동하며, 이어서 애니메이션과 세부사항 화면을 거칩니다.
- 신규 저장 ID는 임시 저장 후보에 생성하며 저장 성공 후 HUD에 확정됩니다.
- 신규 생성, 기존 스킬 수정과 동일 ID 재저장을 확인했습니다. 프로세스 재시작 후 복원은 별도로 확인해야 합니다.

### UI-03: 상태이상 UI 레거시 보존

근거: [상태이상 카드](../Source/SkillMaker/UI/UI-SkillMaker/Common/StatusEffectSelect/SKStatusEffectCardWidget.cpp), [스킬 데이터](../Source/SkillMaker/Skill/SKSkillData.h).

- `FStatusEffectData`, `StatusEffects` 저장 필드와 상태이상 카드 클래스는 향후 버프·디버프 설계를 위해 유지합니다.
- 상태이상 카드는 자체 입력 변경 델리게이트를 계속 제공하지만 현재 상세 위젯은 목록을 생성하거나 구독하지 않습니다.
- 기존 디버프 탭의 화면 위치와 컨테이너는 DONE-UI-01의 속성 선택 UI가 사용합니다.

### UI-04: 선택 UI 상태 복원

- 무기·애니메이션 화면은 진입할 때 HUD의 현재 태그와 몽타주를 전달받아 일치하는 카드의 선택 색상을 복원합니다.
- 세부사항 화면은 HUD의 현재 스킬 타입과 단일 속성을 사용해 기존 설정을 복원합니다.
- 발사체와 노티파이 목록도 HUD의 현재 소프트 클래스와 이름을 받아 선택 텍스트와 카드 색상을 복원합니다. 새 카드를 선택하면 목록 전체를 다시 비교해 이전 카드는 흰색, 새 카드는 파란색으로 즉시 갱신합니다.
- 사용자가 수정 흐름에서 기존 선택의 가시성과 항목 변경 동작이 의도한 수준으로 동작함을 확인했습니다.
- 발사체의 레거시 확인 핸들러와 상세 위젯의 별도 저장 함수는 제거했습니다. WBP에 남은 확인 버튼은 선택적 바인딩으로 찾아 숨깁니다.
- 발사체 목록 구성은 디자인 타임·에셋 검증 월드에서는 GameInstance를 조회하지 않아 WBP 저장 검증을 방해하지 않습니다. 실제 게임 월드의 누락은 오류 로그로 구분합니다.

### UI-05: 생성·수정 모드와 저장 이름 입력

- 메인 위젯은 현재 편집 모드를 `None`, `Create`, `Modify`로 구분하며 공통 편집·저장 단계의 로그에 실제 모드를 표시합니다.
- 신규 생성 흐름을 시작하면 이전 입력값이 남지 않도록 스킬 이름 입력란을 비웁니다.
- 기존 스킬 수정 흐름에서는 선택한 저장 데이터를 불러온 뒤 기존 `SkillName`을 저장 화면의 입력란에 미리 설정합니다.
- 입력값은 편집 흐름을 시작할 때만 설정하므로 저장 화면에서 이름을 바꾸고 이전 화면을 다녀와도 작성 중인 값이 유지됩니다.
- 저장에 성공해 생성·수정 선택 화면으로 돌아가면 화면 이력을 `ChooseAction` 하나로 초기화하고 뒤로가기 버튼을 숨깁니다.
- 위 변경을 포함한 `SkillMakerEditor Mac Development` 빌드가 성공했으며, 사용자가 실제 위젯에서 기존 스킬명 자동 입력과 저장 후 뒤로가기 버튼 숨김을 확인했습니다.

- 위젯 생성, 델리게이트 바인딩, 선택 이벤트 수신, 데이터 설정, Viewport 추가·제거, 가시성·활성화·크기, 포커스, 슬롯 클릭과 GameOnly 복귀에 진단 로그를 추가했습니다.
- 슬롯 버튼을 누르면 전체 `FSKSkillData`를 플레이어 스킬 맵에 등록하고 `SkillID`를 컨트롤러 슬롯에 배치한 뒤 UI를 닫아 GameOnly 입력으로 복귀합니다.

- 사용자가 두 맵의 양방향 이동과 제작 맵에서 새로 저장한 스킬이 훈련장 선택 목록에 즉시 나타나는 흐름을 확인했습니다.
- 스테이션은 별도 위젯을 생성하지 않고 플레이어의 훈련장 HUD에 기존 선택 화면 표시를 요청합니다.
- 상세 위젯은 훈련장 HUD 참조를 받지만 실제 데이터 초기화·저장은 제작 HUD에 의존합니다. 공통 클래스 사용만으로 양쪽 편집이 연결된 것은 아닙니다.
- 컨트롤러는 기존 `BP_SKPlayerController`의 `IMC_Default`와 `IA_SkillQ/E/R/F` 참조를 유지합니다. 정적 에셋 문자열 검사에서 다섯 참조가 모두 존재함을 확인했습니다.
- 스킬 키는 C++ 런타임 Enhanced Input 컨텍스트도 생성해 Q→슬롯 0, E→슬롯 1, R→슬롯 2, F→슬롯 3 연결을 보장합니다. 각 액션은 `Started`에 바인딩해 키를 누르고 있는 동안 반복 실행되지 않으며, 빈 슬롯 입력은 실행하지 않고 경고를 남깁니다.
- 사용자가 저장 스킬 조회 → 캐릭터 SkillMap 등록 → Q 슬롯 배치 → Q 키 입력 → 몽타주·트리거 → 발사체 생성 → `BP_SKAI` 충돌까지 실행 로그로 확인했습니다.
- `IA_OpenSkillChangeUI`를 지정 경로에서 로드해 `Started` 이벤트에 바인딩했습니다. 숫자 `0`의 액션 매핑은 사용자가 설정한 `IMC_Default`를 사용합니다.
- 숫자 0 입력 시 Q/E/R/F의 현재 SkillID를 조회하고 SaveGame의 스킬 이름으로 변환해 매핑 현황 위젯에 표시합니다. 현황 화면의 슬롯 행은 표시 전용이며 `스킬 선택`을 누르면 기존 저장 목록으로 이동해 새 스킬과 배치 키를 선택할 수 있습니다. 사용자가 현황 표시와 재배치 결과 반영을 확인했습니다.
- 훈련장 실행 캐릭터는 `ASKPlayerCharacter`, 투사체 피해 확인 대상은 `ASKAICharacter`입니다. 저장한 피해값 `1000`과 공격자 정보가 발사체에서 공통 `ASKBaseCharacter`의 전투 컴포넌트로 전달되고 대상 체력이 `100000 → 99000`으로 감소하는 실행 결과를 확인했습니다.

## 스킬 실행과 전투

### DONE-COMBAT-01: 발사체 스킬 충격 전달과 직접 피해

근거: [트리거 노티파이](../Source/SkillMaker/Animation/SKSkillAnimNotify_Trigger.cpp), [발사체 구현](../Source/SkillMaker/Skill/SKProjectileActor.cpp), [발사체 헤더](../Source/SkillMaker/Skill/SKProjectileActor.h).

- 노티파이는 몽타주 재생 전에 설정된 `CurrentSkillData`의 `NotifyName`을 비교하여 발사체 클래스를 생성합니다.
- 노티파이는 발사 시점의 `FSKSkillData`에서 애니메이션·노티파이·BlendSpace·발사체 클래스 참조를 제외한 `FSKSkillImpactData`를 만들고 공격자 `SourceCharacter`와 함께 발사체에 복사합니다. 발사체는 지연 생성해 충돌 활성화보다 전투 정보 초기화를 먼저 수행합니다.
- 발사체는 `ASKBaseCharacter` 충돌 시 권한이 있는 대상의 `USKCombatComponent::ApplySkillImpact`로 이 스냅샷을 전달합니다. 현재 최종 피해는 `max(0, DamageValue)`이며 속성·공격자·대상 보정은 `CalculateFinalDamage` 확장 지점에 추가합니다.
- 전투 컴포넌트는 공격자·대상·스킬·속성·기본/최종 피해와 적용 전후 체력을 `LogSkillMaker`로 기록합니다. 상태이상 전체 데이터도 수신하지만 결함이 있는 기존 상태이상 타이머 경로에는 아직 자동 적용하지 않습니다.
- 발사체 시작 시 시각 컴포넌트 활성화와 `ProjectileSound` 재생은 기존 경로를 유지합니다.
- 사용자가 제작 미리보기에서 `SKPreviewCharacter_0`의 피해 `1000`이 `BP_SKAI_C_1`의 체력 `100 → 0`과 사망 처리로 이어지는 것을 확인했습니다.
- 같은 스킬을 저장한 뒤 훈련장에서 E 슬롯으로 실행했을 때 공격자 `BP_SKPlayerCharacter_C_0`, 대상 `BP_SKAI_C_1`, 기본·최종 피해 `1000`, 체력 `100000 → 99000`이 순서대로 기록됐습니다.
- 광역 상태이상 함수는 존재하지만 노티파이에서 호출하는 부분은 주석입니다. [근접 노티파이](../Source/SkillMaker/Animation/SKSkillAnimNotify_HitCheck.cpp)도 타격 함수를 호출하지 않으며 해당 함수의 피해 적용은 미구현 표시로 남아 있습니다.
- 발사체 블루프린트에 지정된 시각 효과와 사운드 출력, 타겟 충돌은 제작 미리보기에서 확인했습니다.

### COMBAT-02: 상태이상 규칙 미준수

근거: [전투 컴포넌트](../Source/SkillMaker/Combat/SKCombatComponent.cpp)의 `MulticastApplyStatusEffect_Implementation`; 기준: [개발 규칙](CONVENTIONS.md)의 전투 규칙.

- 반복 피해와 해제 예약에 같은 `StatusEffectTimers[EffectType]` 핸들을 사용합니다. 타이머 분리 규칙을 충족하지 않습니다.
- Slow는 원본 속도 저장 없이 적용 시 `×0.5`, 해제 시 `×2`를 사용합니다. 중복 적용 또는 다른 속도 변경이 끼면 원래 상태 복원을 보장하지 못합니다.
- 멀티캐스트 안에서 이동 상태와 피해 타이머를 변경합니다. 서버의 상태 변경과 표현 동기화가 분리되어 있지 않습니다.
- Burn·Poison의 피해 코드는 1초마다 고정값 `5.0f`를 사용하며 `DamagePerSecond`와 중첩 설정을 읽지 않습니다. Shock·Curse의 switch 분기 처리도 없습니다.
- 체력 복제와 피해·사망 함수가 발사체의 `ApplySkillImpact` 경로에 연결되었습니다. 상태이상 자동 적용은 별도 수정이 필요합니다.

### NET-01: 실행 권한과 쿨다운의 경로 차이

근거: [스킬 컴포넌트](../Source/SkillMaker/Skill/SKSkillComponent.cpp), [트리거 노티파이](../Source/SkillMaker/Animation/SKSkillAnimNotify_Trigger.cpp), [발사체](../Source/SkillMaker/Skill/SKProjectileActor.cpp).

- 권한이 없는 소유자는 `ServerUseSkill`로 요청하며 서버 구현에서 `IsSkillAvailable`을 검사합니다.
- 권한을 가진 소유자는 `ClientRequestUseSkill`에서 `ExecuteSkill`을 직접 호출하며 이 분기에 쿨다운 검사가 없습니다. 단독 실행·호스트·프리뷰에서 반복 사용을 별도로 확인해야 합니다.
- 몽타주는 멀티캐스트에서 재생됩니다. 노티파이의 발사체 생성과 발사체 충돌·소멸에는 명시적인 권한 검사가 없습니다.
- 발사체 C++ 생성자에 복제 활성화 설정은 없으며 블루프린트 복제 설정은 확인하지 않았습니다. 서버 단독 생성·효과 적용이 보장된다고 문서화할 수 없습니다.

## 데이터 선언과 실행 지원의 구분

근거: [스킬 데이터](../Source/SkillMaker/Skill/SKSkillData.h), 스킬 컴포넌트·상세 위젯·노티파이·전투 컴포넌트의 사용처 검색.

| 필드 | C++에서 확인한 사용 범위 |
|---|---|
| SkillType | Attack/Buff/Debuff 선언과 UI 선택은 있음. 실행 분기는 확인되지 않음 |
| DamageValue | 기본 탭 입력 → HUD → SaveGame → 발사체 충격 스냅샷 → 최종 피해 계산에 사용. 프로토타입 직접 입력이며 장기 계산 규칙으로 교체 예정 |
| MinRange / MaxRange | 구조체·저장·로그에 남아 있음. 활성 상세 UI 편집에는 사용되지 않으며 MaxRange는 비활성 근접·광역 보조 함수에서 참조됨 |
| CooldownTime | 실행 후 쿨다운 기록에 사용. 상세 위젯 C++ 편집 핸들러는 확인되지 않음 |
| Cost / bCanMoveWhileChanneling | 데이터 선언·기본값 외 실행 적용이 확인되지 않음 |
| bAffectEnemies / bAffectAllies | 발사체 충격 스냅샷과 전투 컴포넌트까지 전달·기록. 팀 판별 체계가 없어 대상 필터에는 아직 사용하지 않음 |
| EffectNotifyNames | 배열 선언은 있지만 활성 트리거 경로는 단일 NotifyName을 비교 |
| bCanStack / MaxStack / DamagePerSecond | 데이터·일부 카드 처리는 있음. 전투 적용은 미연결 |
| bUseMoveBlendSpace / MoveSkillBlendSpace | 데이터 필드는 있지만 C++ 실행 적용이 확인되지 않음 |

## 기획과 현재 구현의 차이

- 장기 기획은 플레이어가 최종 피해를 직접 입력하거나 저장하지 않고 제작법·시전자 능력치·장비·대상 방어로 계산하는 구조입니다. 현재 `DamageValue` 입력과 `max(0, DamageValue)` 계산은 전투 전달 경로를 검증하기 위한 프로토타입 임시 구현입니다.
- 발사체는 시전 시점의 스킬 전투 정보와 공격자 객체를 보관하지만 공격자의 능력치 스냅샷은 아직 없습니다. 시전자 능력치는 시전 시 확정하고 대상의 방어·저항은 명중 시 조회한다는 장기 방향을 구현하려면 능력치 데이터와 확정 시점을 먼저 정해야 합니다.
- `bAffectEnemies`와 `bAffectAllies`는 충격 데이터에 포함되지만 팀·진영 판별 체계가 없어 필터링하지 않습니다. 현재는 시전자 자신을 제외한 모든 `ASKBaseCharacter`가 피해 대상입니다.
- 상태이상 전체 데이터는 전투 컴포넌트까지 전달되지만 실제 적용하지 않습니다. 기존 상태이상 구현은 타이머 공유, 고정 주기 피해, 이동 속도 복원과 멀티캐스트 책임 문제가 있어 그대로 연결하지 않습니다.
- 최초 범위는 발사체이므로 근접·자기중심 광역·지면 지정은 실행 경로가 완성되지 않았습니다. 이후에도 같은 `FSKSkillImpactData → USKCombatComponent` 경로를 공통 충격 계약으로 사용할지 결정해야 합니다.
- Q/E/R/F 슬롯은 현재 컨트롤러 메모리에만 있습니다. 제작 스킬은 SaveGame에 남지만 프로세스를 다시 시작하면 슬롯 배치는 복원되지 않습니다.
- 제작 미리보기의 실행 전 검사는 저장 검사보다 느슨합니다. 애니메이션만 먼저 보는 부분 미리보기를 공식 지원할지, 저장과 같은 필수 항목을 요구할지 정해야 합니다.
- C++ 기본 체력은 `100`이지만 확인한 훈련장 `BP_SKAI`는 `100000`을 사용했습니다. 프리뷰 더미와 훈련장 허수아비의 체력 정책을 통일할지, 용도별로 다르게 유지할지 결정해야 합니다.
- 이전에 저장한 스킬의 `DamageValue=0`은 자동으로 보정하거나 이관하지 않습니다. 기존 테스트 스킬을 직접 수정할지, 저장 버전과 마이그레이션 규칙을 둘지 결정해야 합니다.
- 데미지 입력은 현재 `FString::IsNumeric`을 사용하므로 단순 숫자 입력은 처리하지만 천 단위 구분 기호 같은 지역화 형식은 허용하지 않습니다. 프로토타입 입력을 유지한다면 표시 형식과 입력 파싱 규칙을 맞춰야 합니다.
- `USKSkillSelectionWidget::OnSkillSelected`는 C++ 델리게이트 구독과 빌드는 동작하지만 UPROPERTY 지정자가 `BlueprintCallable`입니다. 블루프린트 이벤트 구독을 공개할 계획이면 `BlueprintAssignable` 계약으로 정리해야 합니다.

## 실행 검증이 남은 항목

- `SkillMakingMap` 외 다른 맵의 월드 설정 및 GameMode 재정의.
- 누락된 몽타주 트리거의 노티파이 클래스·이름·저장 상태와 속성에 따른 실제 이펙트 색상 처리.
- 부분 미리보기와 완성 미리보기의 검증 정책 및 사용자 안내 구현.
- 무기·애니메이션 데이터 테이블의 Gameplay Tag와 필수 참조 자동 검증.
- 제작 UI의 현재 세션 수정 복원과 맵 왕복 후 새 저장 스킬 조회는 확인했습니다. 프로세스 재시작 후 SaveGame 복원과 스킬셋·슬롯 영속화는 별도로 확인해야 합니다.
- 패키징에서 데이터 테이블과 그 안의 소프트 참조 에셋이 실제 쿠킹 대상에 포함되는지 확인. 문자열 경로로만 찾는 테이블은 패키징 의존성 추적 여부를 별도로 검증해야 함.
- 리소스 수가 늘어날 때 스킬 로드 단계의 선행 로드·캐시 정책과 스크롤 목록의 페이징·가상화 필요성 검토.
- 호스트·클라이언트별 쿨다운, 발사체 생성 개수, 상태이상·피해·소멸의 권한과 복제.

에디터 타깃 C++ 빌드와 `SkillMakingMap` 명령행 로드가 성공했고, 사용자가 신규 생성·기존 수정 흐름, 수정 시 모든 기존 선택의 표시와 변경, 세부사항의 탭·스크롤·속성·피해값 선택, 기존 스킬명 자동 입력, 저장 후 이동 이력 초기화와 뒤로가기 버튼 숨김을 실제 UI에서 확인했습니다. 제작 미리보기의 발사체 이펙트·사운드·충돌·피해·사망, 제작·훈련장 맵 왕복, 제작 스킬 조회, Q/E/R/F 슬롯 배치와 지정 키 실행, 숫자 0 매핑 현황 표시와 재배치도 확인했습니다. 훈련장에서는 저장된 피해 `1000`과 공격자·대상 정보가 발사체를 거쳐 `USKCombatComponent`에 전달되고 대상 체력이 `100000 → 99000`으로 감소했습니다. 이로써 최초 프로토타입의 핵심 사용자 흐름은 완료됐습니다. 일부 트리거 누락, 상태이상, 장기 피해 계산식, 프로세스 재시작·패키징·멀티플레이 검증은 후속 범위입니다.
